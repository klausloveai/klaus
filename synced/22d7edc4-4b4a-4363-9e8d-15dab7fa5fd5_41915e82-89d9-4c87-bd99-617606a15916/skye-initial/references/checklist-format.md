# 材料清单 — 格式与写法

本文件是律所现有材料清单的成文规范，取自五份真实清单（Chen Yang、Chujun Yang、
Qing Yang EB1A、Jiewen Wang O1、Xixi Shen O1A）。新建和更新清单都照这个来，
不要另发明一套 —— 同事是按肌肉记忆扫这份文档的，换了结构就得重新读。

## 版面（Google Docs 实测所得，不是猜的）

| 元素 | 样式 |
|---|---|
| 全文 | Times New Roman 12pt |
| 第一行标题 | **加粗**，`{英文全名} {案件类型} 材料清单` |
| 标题下的案件状态行 | 普通文本；「加急」这类可加黄色高亮 |
| 章节标题 | 普通文本，不加粗、不用 Heading 样式，以全角「：」结尾 |
| 正文 | 圆点项目符号（●○■），用 Tab 缩进控制层级 |
| 章节之间 | 空一行 |

律所现有清单里**没有一个**用 Docs 的 Heading 样式。新清单若用了，打开时字号
字体全变，和旧清单摆在一起一眼就是两套东西。`checklist.py` 已经按这套写，
不要绕过它直接调 Docs API。

## 头部信息块

标题下面逐行列已知的案件状态，只写知道的，不知道的整行不写：

```
DDL：10/01/2026
加急              ← 或「先不加急」
COS:H1B➡️O1        ← 身份转换路径
O1 Start date: 1/1/2027(保守)
原O-1 IOE8342503951 https://egov.uscis.gov/
```

## 章节顺序

章节名用中文短名（下表左列），这是同事口头和文档里都在用的叫法。

**EB1A**
```
个人信息：/ 奖项：/ 会员：/ 新闻：/ 评审：/ 原创贡献：/ 学术发表：/ 展览：/
重要组织重要角色：/ 高薪：/ 商业成就：/ Final Merits：/ 未来计划：
```

**O-1A**
```
个人信息：/ 工会信：/ Maintenance of Status：/ 未来计划：
O1A 8满3：                       ← 这一行是分隔标记，下面才是八条标准
会员：/ 奖项：/ 新闻：/ 评审：/ 原创贡献：/ 学术发表：/ 重要组织重要角色：/ 高薪：
```

**O-1B** 同 O-1A 的头四节，分隔行写 `O1B 6满3：`，其下六条为
```
主演主创：/ 国家级国际级认可：/ 知名机构主要角色：/ 商业或口碑成就：/
业内专家认可：/ 高薪：
```

**NIW**
```
个人信息：/ Proposed Endeavor：/ Prong 1：/ Prong 2：/ Prong 3：/
推荐信：/ 未来计划：
```

O-1 把「工会信 / Maintenance of Status / 未来计划」放在标准之前，是因为这三样
决定案子能不能递、什么时候递，比凑够几条标准更早卡人。EB1A 没有身份问题，
所以直接从证据开始。

一个客户走两条线（`EB1A+O1`、`NIW 先 O1 后`）时，**一份清单，不是两份**：主线
写完，加一行 `________________` 分隔，再写第二条线的章节。Jiewen Wang 那份就是
O-1 全文之后接 `NIW：`。两份文档会各改各的，一个月后没人知道哪份是准的。

## 条目怎么写

一级项目符号 = 一个**条目**（一个奖、一次评审、一篇报道、一家机构）。
它下面的子项 = 这个条目要收齐的**证据件**，以及还差什么。

```
* Red Dot 2026 - Sofia
	* 获奖通知邮件（已有）
	* 官方 release 10/15 公布，公布后上传奖状
* Orpetron Web Design Awards 402 个 ✅
	* 邀请邮件 / 官网 listing
	* 实际参与评审证据：总数页面 PDF + 具体项目评审页 10 个
	* certificate
```

条目行末尾写数量（`402 个`、`50 个`、`9 人`）—— 评审和展览的说服力就在数量上，
写在条目行上，扫一眼就知道这条够不够。

## 状态与责任标记

| 标记 | 含义 | 用在哪 |
|---|---|---|
| `✅` | 这一项证据已收齐 | 条目行末或证据行末 |
| `（已有）` | 客户已提供 / 卷宗里已有 | 证据行末 |
| `🉑` | 已审核可用（多用于新闻） | 报道行末 |
| `上传` / `客户提供：` | 客户要做的事 | 行首或行末 |
| `律所调研` / `律所帮忙找` / `律所draft` | 律所要做的事 | 行末 |
| 无标记 | 还没有，待补 | — |

「客户要做」和「律所要做」必须在同一行里分得出来。这份清单同时是给客户的催件
依据和律所的待办表，一行不写清谁负责，两边都会以为对方在做。

## 反复出现的固定说法

这些是律所审过的措辞，照抄，不要重写：

**新闻**
```
新闻需要有具体作者姓名，有发布日期，需要是主流媒体平台（浏览量/点击量在百万），
新闻报道不能是 Q&A 形式，内容围绕您 or 您的作品，需要是第三方叙述口吻；
```
补充要点：不含 disclaimer；作者不能是「编辑部」；发之前给律所看 draft；
间隔一个月左右发一篇。

**推荐人信息**
```
推荐人 legal name / title / email / linkedin or 简历（公司主页可以）
```

**评审证据三件套**
```
* 资格：邀请函 / 邀请邮件 / 评委证 / 官网 listing
* 完成证明：certificate / 感谢信 / 证明信
* 工作记录：打分表 / 打分 sample（5 个左右）/ 能体现总评审个数的页面（存 PDF，保留页眉页脚）
```

**展览证据**
```
* 邀请函 / 参展证明
* 展览现场照片，多角度：作品特写（能显示 credit）、展览场所整体、有人参观
```

**重要组织重要角色**
```
* 重要角色：Offer / Title / promotion letter / W2 / 最近三个月 payroll
	* 负责项目简要说明：您具体做了什么，产生了怎样的 impact，尽量量化
* 重要组织：律所调研 —— 公司规模与经营情况 / business model / 行业排名 /
  第三方新闻报道 / 融资信息 / 合作品牌 / 权威机构认可
* 推荐信 2 封：最好 C-level 一位 + Department Head 一位
```

**Final Merits（EB1A）**
```
* 独立推荐人 2 位，同领域成就在客户 2-3 倍以上，写推荐信说客户是 top of the field
* 整体成就时间线是否持续：最早追溯到 ____ 年
```

## 首次生成时的取舍

第一版清单是**开会用的底稿**，不是完成品。所以：

- 客户已上传的材料，写成条目 + `（已有）`/`✅`，让会上能直接跳过；
- 该案件类型要求但客户还没给的，**留空条目在那**（只写标准名和证据要求），
  会上逐条问；
- 别替客户编条目。清单里出现一个客户没有的奖，比空着更糟 —— 会上要花时间
  澄清，客户还会以为律所记错了案子。

## 更新时的铁律

**永远不要整篇重写。** 每一份真实清单里都挂着 Google Docs 评论串（律师问
「两位 principal 可以吗」，助理在下面答），还有同事在两次运行之间手改的内容。
整篇替换会让所有评论变成孤儿、把手改内容默默吞掉。

新材料进来只做两件事：
1. `checklist.py insert --section` 往对应章节末尾追加行；
2. `checklist.py mark` 给已存在的行打 `✅` / `（已有）`。

改一个条目的措辞属于人的判断，交给同事，不要顺手替他改。
