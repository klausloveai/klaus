# I-129 field map — edition 02/27/26, 38 pages (O-1A / O-1B)

Derived by walking the widget tree of the 02/27/26 blank and cross-reading three
filed precedents. **YUQIAN TAO_O1A (Aug 2026) is the one to lean on** — it is on
this same 02/27/26 edition, so both its field names and its values transfer.
Xiran Liu O-1B (self-petition, no G-28) and Ziqing Shi O-1B (attorney-filed) are
on the superseded 01/20/25 edition and are useful for values only.
Re-verify with `uscis_forms.py fetch i-129` before reuse — if USCIS publishes a
new edition, names and pages can move and this file needs rebuilding.

Every name below is a suffix. The full key passed to `fill` is
`form1[0].#subform[N].<name>` — take the exact string from
`uscis_forms.py dump forms/i-129.pdf --pages <n>` rather than retyping it, since
the `#subform` index is what binds a field to its page.

F = FIXED (firm standing data) · P = PETITIONER data · B = BENEFICIARY data.
On an O-1 the petitioner is the **employer or agent**, not the beneficiary —
except in a self-petition through the beneficiary's own company, where one
person legitimately fills both roles.

| 2 | `Line3_CompanyorOrgName[0]` | petitioner company/org name — **only if the petitioner is a company** | P |
| 3 | `Line7a_InCareofName[0]`, `Line7b_StreetNumberName[0]`, `Line3_Unit[0..2]`, `Line3_AptSteFlrNumber[0]`, `Line_CityTown[0]`, `P1_Line3_State[0]`, `P1_Line3_ZipCode[0]`, `P1_Line3_Country[0]` | petitioner's mailing address | P |

| 7 | (page 2) petitioner SSN | only for an individual petitioner | P |

Item 1 and item 2 are mutually exclusive — the form says complete item 1 if an
individual is petitioning, item 2 if a company is. Filling both invites an RFE
about who the petitioner actually is.

`Line3_Unit` is a three-way radio whose export values carry literal spaces:
`"/ APT "`, `"/ STE "`, `"/ FLR "`. Passing `"STE"` silently ticks nothing. The
same pattern repeats on every address block in the package.

## Part 2 — Information About This Petition (page 2)

| Item | Field | Value |
|---|---|---|
| 1 | `Part2_ClassificationSymbol[0]` | `O-1A` or `O-1B` — write it hyphenated the way USCIS does; one precedent used `O1B`, which is sloppy rather than wrong |
| 2 | `new[0]` = `/1` | "New employment" (the field really is named `new`) |
| 3 | `Line1_ReceiptNumber[0]` | most recent receipt number, or `None` |
| 4 | `P2Checkbox4[0..5]` → `/A`…`/F` | Requested Action. `/A` = "Notify the office in Part 4 so each beneficiary can obtain a visa or be admitted" (consular notification — both precedents, beneficiary abroad or getting a visa). Use `/B` when the beneficiary is inside the US and needs change of status |
| 5 | `TtlNumbersofWorker[0]` | `1` — O-1 is capped at one beneficiary per petition |

**Item 4 is the CP-vs-COS decision, and it is supplied as an input** — the
instruction that starts the job says which one this case is. Verified against the
printed labels:

| Export | Printed option | Means |
|---|---|---|
| `/A` | a. "Notify the office in Part 4. so each beneficiary can obtain a visa or be admitted" | **CP** — consular processing |
| `/B` | b. "Change the status and extend the stay of each beneficiary…" | **COS** — change of status in the US |
| `/C` / `/D` / `/E` / `/F` | extend stay · amend stay · FTA extend · FTA change | not used on an initial O-1 |

Only one box. Option b. is printed as available only when Part 2 item 2 is "New
employment", which an initial O-1 is, so there is no conflict.

**Part 4 item 1 (consulate type, city, country) gets filled either way** — the
item's own wording covers the case where a change of status cannot be granted, so
a COS filing still names a consulate as the fallback. Do not leave it blank
because the case is COS.

On a COS case, Part 3 item 6 (current status and its expiry) must be complete, or
the officer cannot assess eligibility to change status.

## Part 3 — Beneficiary Information (pages 2–3)

| Item | Field | Value |
|---|---|---|
| 1 | `P3Line1_Checkbox[1]` = `/Y` | Named (`[0]` = `/N` = Unnamed, H-2 only) |
| 3 | `Part3_Line2_GivenName[0]` / `Part3_Line2_FamilyName[0]` | beneficiary name (field says Line2, printed item is 3) |
| 5 | `Line6_DateOfBirth[0]` | mm/dd/yyyy |
| 5 | `Line1_Gender_P3[0]` = `/M` or `[1]` = `/F` | sex |
| 5 | `Part3Line4_CountryOfBirth[0]`, `Part4Line3_DProvince[0]`, `Part3Line4_CountryOfCitizenship[0]` | birth country, **province of birth**, citizenship. `Part4Line3_DProvince` sits in Part 3 despite its name |
| 6 | `Part3Line5_DateofArrival[0]`, `Part3Line5_ArrivalDeparture[0]` (I-94 number), `Part3Line5_PassportorTravDoc[0]`, `Line_CountryOfIssuance[0]`, `Line11e_ExpDate[0]` (passport expiry) / `[1]` (issue date), `Line11g_CurrentNon[0]`, `Line11h_DateStatusExpires[0]` (date or `D/S`) | only if the beneficiary is in the US |

`Line11g_CurrentNon` is a **choice field with 151 options**, displayed as
`CODE - DESCRIPTION` but exported as the bare code — write `L1A` or `F1`, never
the description. Every `_State` field on the form is likewise a choice field
taking a two-letter code.

**Current status and its expiry come from the I-94, and only from the I-94.**
The I-94's `Class of Admission` is `Line11g_CurrentNon`; its `Admit Until Date`
is `Line11h_DateStatusExpires` — copy `D/S` through verbatim rather than
converting it to a date. Do not derive either value from an I-20, a visa page, or
a case note: an I-20's OPT end date and the I-94's admit-until date are different
facts, and confusing them misstates the record.

If the case folder has no I-94, pull one from
`https://i94.cbp.dhs.gov/search/recent-search` ("Get Most Recent I-94") using the
beneficiary's surname, given name, date of birth, passport number and passport
country of issuance — all of which the other Part 3 fields already need — then
**save the result as a PDF into the case's forms folder before filling these two
boxes.** The saved PDF is the only artifact that shows where the two values came
from, which is what makes them checkable by a colleague or an officer.

An I-94 reflects only the **most recent admission**. Changing schools or moving
onto CPT/OPT does not generate a new I-94, so `Class of Admission` stays whatever
the last entry was. When the I-94 on file is more than a year old, re-pull it to
confirm there has been no newer admission rather than trusting the stored copy.
| 7 | `Line8a_StreetNumberName[0]`, `Line6_Unit[0..2]`, `Line6_AptSteFlrNumber[0]`, `Line8d_CityTown[0]`, `Line8e_State[0]`, `Line8f_ZipCode[0]` | current US residential address, no P.O. box |

`Line11e_ExpDate[0]` vs `[1]` are the passport **expiry** and **issue** dates and
sit adjacent on the page — check the rect from `dump` before assigning, because
swapping them is invisible on a quick read and wrong on the record.

| 10 | `Line10_Explanation[0]` | other compensation — **and, when the case has more than one offer at different wages, this box must carry `Different wage for different project.`** See below |
| 11 | `Part5_Q10_DateFrom[0]` / `Part5_Q10_DateTo[0]` | **both dates come from the client's offer / employment agreement**, which states the O-1 period. Max 3 years for an initial O-1. | 12 | `Part5Line12_TypeofBusiness[0]` | petitioner's type of business (`Agent` when filing through an agent) |
| 13 | `P5Line13_YearEstablished[0]` | year established |
| 14 | `P5Line14_NumberofEmployees[0]` | US employees |
| **15** | `P5Line15_Yes[0]` **or** `P5Line15_No[0]`, value `/Y` | **25 or fewer full-time-equivalent US employees?** |
| 16 | `Line15_GrossAnnualIncome[0]` | gross annual income |
| 17 | `Line16_NetAnnualIncome[0]` | net annual income |

**Multiple offers at different wages.** When the case file holds two or more
offers with different rates (e.g. $65/hour from the petitioner and $100/hour from
another company), item 9 takes the rate from **the offer this petition is built
on**, and item 10 must then explain the spread:

> Different wage for different project.

Leaving item 10 empty makes item 9's single figure contradict the other offers in
the exhibit set, and "the record is internally inconsistent" is one of the
easiest things for an officer to write up. One sentence in item 10 converts it
into an explained fact.

Item 15 is the highest-stakes checkbox in the package: it is the Small Employer
declaration, and it has to agree with the fee amounts on the G-1650s. Yes here
means $530 + $300; No means $1,055 + $600. A mismatch between this box and the
ACH amounts is a rejection or an underpayment, so check it against item 14 and
against the G-1650s before assembling.

Item 15 is also where the 02/27/26 edition changed mechanism — see
[Edition drift](#edition-drift-012025--022726).

## Part 6 — Controlled Technology certification (page 6)

| Item | Field | Meaning |
|---|---|---|
| 1 | `NoDeemed[0]` = `/1` | no export license required |
| 2 | `Deemed[0]` = `/1` | a license is required and access will be withheld until granted |

**Required for O-1A, not for O-1B.** The form says so itself in the section
header. The Aug 2026 O-1A filing selects **item 1** (`NoDeemed[0]` = `/1`, no
license required), which is the firm's normal answer; select item 2 only when a
license genuinely is required. Never both.

The two O-1B precedents have this part blank, correctly — do not read their
blankness as "optional" when the case is an O-1A.

## Part 9 — Additional Information (page 8 onward)

Each continuation entry is a label triple (page / Part / item) plus a text box,
and **the two are not numbered in step**. Three pairings confirmed on the Aug
2026 filing:

| Label group | Text box | What it held |
|---|---|---|
| `Line2a/2b/2c_PageNumber/PartNumber/ItemNumber` | `Line2_AdditionalInfo[0]` | full foreign address (page 4, Part 4, item d) |
| `Line4a/4b/4c…[1]` | `Line3_AdditionalInfo[0]` | why weekly hours vary (page 5, Part 5, item 8) |
| `Line4a/4b…[0]` | `Line4_AdditionalInfo[0]` | why no labor organization exists (page 29, Part 8) |

Confirm the pairing by rect on the page you are filling rather than assuming the
indices line up — they demonstrably do not.

| 4 | `Line3_JobDescription[8]` | explain the nature of the event (e.g. `Motion Picture Production`) |
| 5 | `Line3_JobDescription[7]` | describe the duties — one or two lines plus "See details in attached documents." |
| 6 | `Line3_JobDescription[6]` | dates of prior work experience under the O-1/P principal — **O-2 and P support classifications only**, leave blank on an O-1 |

Both name fields are single wide boxes, so the full name goes in one string —
they are not split family/given despite the field names. Note the two are in the
reverse of the order the field names suggest: `Line1_FamilyName[5]` is the
petitioner and `HSupLine2_FamilyName[1]` is the beneficiary. Confirmed by rect
and by rendering a filled page.

Item 7.a is `Yes` in exactly the self-petition case (beneficiary owns the
petitioning company) and `No` when a third-party employer or agent petitions.
Getting it wrong contradicts the ownership documents in the exhibit set.

## Edition drift 01/20/25 → 02/27/26

The **YUQIAN TAO_O1A** filing (Aug 2026) is already on 02/27/26, so nothing in
this file needs translating for it. The two January 2026 precedents are on the
**01/20/25** edition, which is superseded.
A full name-by-name diff of the two editions found 28 removals and 38
additions, and all but one sit in the H-1B supplement. The one that touches
O-1 filings:

| 01/20/25 | 02/27/26 | Consequence |
|---|---|---|
| `P5Line15_CB[0]` / `[1]` (one radio group, page 6) | `P5Line15_Yes[0]` / `P5Line15_No[0]` (two independent checkboxes, both on-state `/Y`) | Copying the old key applies nothing at all, and the Small Employer answer silently goes blank |

Everything else the O-1 package touches — Parts 1–9 and the whole O and P
supplement, pages 28–30 — kept identical names, indices and pages. That is why
the precedents remain usable as a source of *values*; they are no longer a
source of *field names*. When the next edition lands, rerun this same diff
(`get_fields()` key sets, old vs new) before trusting any row above.
